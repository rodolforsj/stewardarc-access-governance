# ADR-004 — Initial Data Model Baseline

- **Status:** Accepted
- **Date:** 2026-09-15

## Context

[ADR-001](0001-backend-architecture-baseline.md) established a modular monolith with a shared consistency boundary for the Access Governance domain. [ADR-002](0002-technology-stack-baseline.md) selected PostgreSQL and Eloquent. [ADR-003](0003-lifecycle-state-and-persistence-baseline.md) decided that the Access Request current state (`S1`–`S5`) is persisted, that the Granted Access state (`A1`–`A3`) is derived from preserved facts, the effective validity period and time, and that a functional fact and the related state change belong to the same PostgreSQL transaction.

Before the first migrations can be written, the project needs a persistence baseline: which tables exist, which identifiers are used, and which invariants the database itself guarantees.

The decision is driven by:

- `RN03` — no equivalent request in processing and no equivalent active access;
- `RN07` — the duration of a Privileged request, greater than zero and at most 90 days;
- `RNF-003` — functional history integrity;
- `RNF-004` — attribution and temporal coherence;
- `RNF-008` — consistency under failures;
- `RNF-009` — consistency under concurrency and repetition.

The column-level detail lives in [data-model.md](../data-model.md); this ADR records the decisions behind it.

## Decision

Adopt an initial data model baseline with the following architectural choices.

- **Identifiers.** Persisted identifiers use the PostgreSQL `uuid` type and hold UUIDv7 values generated by the application. No sequences, `serial`/`bigserial`, UUIDv4 baseline, PostgreSQL extension or database-generated UUID.
- **Actor Reference separated from authentication.** `actor_references` represents a person referenced by the domain. It is not an authentication table and holds no password, token, secret or credential. An opaque, stable `external_identity_key` allows a future mapping to the authenticated identity.
- **One Resource Owner per Resource.** In the MVP, a resource carries exactly one Resource Owner actor reference. No pivot table and no multiple owners. This is an MVP decision, not a statement about future versions.
- **Tables.** Eight tables: `actor_references`, `resources`, `access_profiles`, `access_requests`, `decisions`, `grant_confirmations`, `granted_accesses` and `revocation_confirmations`.
- **Approval flow snapshot.** An Access Request stores the approval flow determined when it was created, so a historical request is not reinterpreted if the catalog changes later.
- **Privileged duration in whole seconds.** The requested duration is persisted as a positive integer number of seconds, bounded by 7,776,000 seconds (90 × 24 × 60 × 60). This is an internal technical representation; the functional wording of `RN07` is unchanged.
- **Functional facts in their own tables.** Decisions, grant confirmations and revocation confirmations are preserved facts, each with its actor reference and its own semantic timestamp.
- **No persisted state on Granted Access.** `granted_accesses` has no state, status, lifecycle, expired or revoked column. `A1`/`A2`/`A3` remain derived, per ADR-003. The effective validity starts at the grant confirmation's `recorded_at`, and `valid_until_at` holds the effective end when a calculable end exists.
- **No Functional History table.** Functional History stays a projection over the preserved facts. There is no history, audit log, events or domain events table, and no expiration table.
- **Controlled values as text plus CHECK.** Classification, approval flow, current state, decision stage and decision outcome are `text`/`varchar` columns constrained by CHECK, not PostgreSQL native enums.
- **Restrictive foreign keys.** Foreign keys use restrictive behavior (`RESTRICT`/`NO ACTION`). No destructive cascade delete reaches access requests, decisions, grant confirmations, granted accesses or revocation confirmations. No soft delete is introduced for functional facts in this baseline.
- **`RN03` partially enforced in the database.** A unique partial index over the requester and the access profile, restricted to requests in `S1`, `S2` or `S3`, prevents two equivalent requests in processing at the same time. The half of `RN03` about an equivalent active Granted Access is not enforced in the database by this baseline.

## Rationale

These choices are contextual to StewardArc, not claims of universal superiority.

- **UUIDv7** gives non-sequential identifiers with better temporal locality than fully random UUIDs, which keeps inserts reasonable without exposing sequential counters.
- **Generating identifiers in the application** avoids depending on a PostgreSQL extension and keeps the identifier available before the row is written.
- **`actor_references`** keeps the authenticated identity outside the domain, as the architecture requires, while still giving facts a stable subject to point at.
- **One owner per resource** keeps the MVP aligned with the current rules without inventing semantics for multiple approvers that no rule describes.
- **The approval flow snapshot** preserves the historical interpretation of a request even if the profile's classification changes later.
- **Whole seconds** give a simple technical representation for the duration without changing the functional language of `RN07`, which states only "greater than zero and at most 90 days".
- **Separate fact tables** preserve authorship and time and avoid collapsing history into the current state, supporting `RNF-003` and `RNF-004`.
- **No persisted state on Granted Access** respects ADR-003 and avoids a job whose only purpose is to record that time has passed.
- **Text plus CHECK** avoids the rigidity of native enums while still constraining the accepted values.
- **Not declaring `RN03` fully solved** is deliberate: the missing half depends on a derived state and on concurrency, and pretending a constraint covers it would be false precision.

## Consequences

Positive:

- The first migrations have an auditable reference instead of being invented file by file.
- The database guarantees the value vocabularies, the single decision per stage, the single grant confirmation per request and the single revocation confirmation per granted access.
- Preserved facts keep authorship and semantic timestamps.
- The Granted Access lifecycle stays consistent with ADR-003 with no redundant state to keep in sync.

Trade-offs:

- UUIDs take more space than sequential integers and are less readable in manual inspection.
- `actor_references` will require a future mapping from the authenticated identity.
- One Resource Owner per resource deliberately limits the MVP.
- Whole seconds fix the persisted technical resolution of the duration.
- Granted Access queries must derive `A1`/`A2`/`A3` from facts, validity and time.
- `RN03` still requires an additional decision for the equivalent active access case.
- CHECK constraints require a migration whenever a controlled vocabulary changes.

## Deferred decisions

The following remain open:

- authentication;
- session;
- concrete source of the Governance authority;
- concrete mechanism for the concurrent enforcement of the `RN03` half about an equivalent active Granted Access;
- isolation level;
- optimistic or pessimistic locking;
- retry;
- idempotency;
- any proactive time-related processing;
- performance indexes beyond those motivated by integrity;
- observability;
- detailed API contracts;
- testing strategy;
- CI;
- deployment;
- cloud and hosting;
- future version update policy for the stack;
- Laravel and Eloquent implementation details not required by this baseline.

## Relationship to previous ADRs

ADR-004 complements [ADR-001](0001-backend-architecture-baseline.md), [ADR-002](0002-technology-stack-baseline.md) and [ADR-003](0003-lifecycle-state-and-persistence-baseline.md) and does not rewrite them.

- It does not change the approved lifecycles or the approval flows.
- It does not turn `A2` into a persisted state.
- It does not decide concurrency control; it only records which invariants the initial schema guarantees and which remain open.
