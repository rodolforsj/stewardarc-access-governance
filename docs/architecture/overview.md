# Architecture overview

This document records the architectural drivers, constraints and approved baseline of StewardArc, and the decisions that remain deliberately open. The conceptual domain is described in [domain-model.md](domain-model.md).

## Architectural drivers

- **Consistency across the lifecycle.** A decision, the resulting state transition, the grant confirmation, the creation of the Granted Access and the functional history must remain coherent with each other.
- **Failure consistency.** A failure must not leave these facts inconsistent (`RNF-008`).
- **Concurrency and duplicate prevention.** Concurrent or repeated operations must not produce inconsistent states or duplicates (`RN03`, `RNF-009`).
- **Authority and sequence.** Authorization belongs to the product and must enforce who can decide and when (`RN04`, `RN09`, `RN11`, `RNF-001`).
- **Functional history integrity and attribution** (`RNF-003`, `RNF-004`).
- **Controlled MVP scope.** Three actors, two request flows, two lifecycles.

## Constraints

- **Approval ≠ grant.** StewardArc records decisions and confirmations; it does not provision or revoke access in target systems.
- **Identity is external.** The authenticated identity is provided outside the domain.
- **Accessibility.** User-facing interfaces meet the applicable WCAG 2.2 A and AA criteria (`RNF-007`).
- **Data minimization** for functional data and operational information (`RNF-005`, `RNF-006`).

## Guardrails

- Do not split the Access Governance domain across boundaries that would break its consistency.
- Do not treat operational telemetry as functional history, or the reverse.
- Do not introduce performance targets without a real driver.
- Do not select technology by convention; record technical decisions when a driver exists.
- Do not describe components, modules or infrastructure before they are decided.

## Approved baseline

The backend architecture baseline is a **modular monolith with a shared consistency boundary for the Access Governance domain**. See [ADR-001](adr/0001-backend-architecture-baseline.md).

This architecture baseline does not adopt full DDD, formal Clean Architecture, formal Hexagonal Architecture, CQRS, event sourcing or microservices.

The technology stack baseline (PHP + Laravel with Eloquent, PostgreSQL, React + TypeScript + Vite, REST/JSON and Docker Compose for the local environment) is recorded in [ADR-002](adr/0002-technology-stack-baseline.md), which complements ADR-001 without changing it and deliberately did not fix versions.

The executable scaffold later materialized concrete versions through Docker images and lockfiles ([compose.yaml](../../compose.yaml), [backend/Dockerfile](../../backend/Dockerfile), [backend/composer.lock](../../backend/composer.lock), [frontend/package-lock.json](../../frontend/package-lock.json)). These versions form the current executable baseline; those files remain the technical source for them. The Docker Compose environment is for local development only: the backend and frontend development servers are published on the host's loopback interface only, PostgreSQL is reachable only inside the Compose network, and the Keycloak of the optional login demonstration starts only on request and is loopback-only as well. This is a property of the local materialization, not a deployment decision.

The lifecycle state and persistence baseline is recorded in [ADR-003](adr/0003-lifecycle-state-and-persistence-baseline.md): the current Access Request state (`S1`–`S5`, including `S3`) is persisted; the Granted Access state (`A1`–`A3`), including expiration (`A2`), is determined from preserved functional facts, the effective validity period and time; and a functional fact and the related change of the Access Request current state are made in the same PostgreSQL transaction.

The initial data model baseline is recorded in [ADR-004](adr/0004-initial-data-model-baseline.md) and detailed in [data-model.md](data-model.md): eight tables covering the catalog, access requests and preserved functional facts, application-generated UUIDv7 identifiers, controlled values as text with CHECK constraints, restrictive foreign keys, no persisted state column for Granted Access and no table for Functional History.

The concurrency and invariant enforcement baseline is recorded in [ADR-005](adr/0005-concurrency-and-invariant-enforcement-baseline.md): mutations run at PostgreSQL `READ COMMITTED`; commands that change an existing Access Request or Granted Access take a pessimistic row lock on it; and `RN03` is serialized by a transaction-level PostgreSQL advisory lock, deterministic per requester and access profile, taken by request creation, grant confirmation and revocation confirmation, with the invariant re-checked inside it. The unique partial index remains as a structural second line of defense. Request creation materializes this advisory lock; decisions materialize the pessimistic row lock on the Access Request; grant confirmation materializes the advisory lock followed by the Access Request row lock; and revocation confirmation materializes the advisory lock followed by the Granted Access row lock. The three operations that take part in the `RN03` serialization — request creation, grant confirmation and revocation confirmation — are therefore materialized in the order decided by ADR-005 and ADR-006.

The application implementation baseline is recorded in [ADR-006](adr/0006-application-implementation-baseline.md): Eloquent models stay in `App\Models`, future functional operations live in `App\AccessGovernance\Actions` and PostgreSQL-specific concurrency mechanisms in `App\AccessGovernance\Concurrency`; each critical Action owns its own transaction; the advisory lock key is a namespaced SHA-256 derivation passed to `pg_advisory_xact_lock(integer, integer)`; locks are acquired advisory first, then row; and database-dependent tests run against real PostgreSQL. The slices implemented under these namespaces are Request access (UC-001 / RF-002, with the catalog consultation of RF-001 / CA-001 in `ConsultAccessCatalog`, a plain single-statement read of the profiles currently available for new requests, outside ADR-008 because it has no compound projection or temporal derivation), Decide access request (UC-002 / RF-004 and RF-005), Confirm external access grant (UC-003 / RF-006), Record external access revocation (UC-004 / RF-007), Follow my requests and accesses (UC-005 / RF-009, RF-010 and RF-011 in the Requester scope) and Consult accesses and history within responsibility scope (UC-006 / RF-010 and RF-011 in the Resource Owner and Governance scopes).

The governance authority baseline is recorded in [ADR-007](adr/0007-governance-authority-baseline.md): the current Governance authority is a minimal association, `governance_memberships`, whose single column `actor_reference_id` is at once primary key and foreign key to `actor_references`. Resource Owner authority keeps coming from the resource itself, the two authorities may overlap in the same actor, and `RN04` still forbids deciding one's own request. The association is materialized — the executable schema now has nine domain tables — and it is already the source of Governance authority used by the decision slice.

The read projection consistency baseline is recorded in [ADR-008](adr/0008-read-projection-consistency-baseline.md): the compound functional read projections of `UC-005` and `UC-006` run in one short PostgreSQL `REPEATABLE READ READ ONLY` transaction, so each projection — including its authorization scope reads — observes a single snapshot, and every temporal derivation in it uses one `projection_reference_at`, taken from `transaction_timestamp()`. Projections take no row or advisory locks and are fully materialized before their transaction ends. Functional History remains a projection over the preserved facts, with expiration as a derived milestone without an actor. Isolation is therefore scoped: mutations keep `READ COMMITTED` with the locking of ADR-005 and ADR-006, while compound read projections follow ADR-008; the global default is unchanged. `ReadProjectionTransaction`, in `App\AccessGovernance\Concurrency`, materializes this read transaction: it refuses to join an outer transaction, sets `REPEATABLE READ, READ ONLY` before any other query and takes `projection_reference_at` from `transaction_timestamp()`. `FollowMyRequestsAndAccesses` (`UC-005`) is the first projection built on it: it reads the Requester's own requests, Granted Accesses and Functional History in that one snapshot, derives `A1`/`A2`/`A3` against that single instant, takes no row or advisory lock and returns a fully materialized result. `ConsultAccessesAndHistoryWithinResponsibilityScope` (`UC-006`) is built on the same transaction: inside that snapshot it reads the actor's current Governance membership and returns the union, without duplicates, of the requests for resources the actor currently owns and, for Governance members, the requests whose `approval_flow` snapshot is `privileged`, in any state, with the same Granted Access derivation and Functional History as `UC-005` and each requester identified by id and display name.

The functional time source baseline is recorded in [ADR-009](adr/0009-functional-time-source-baseline.md): PostgreSQL is the canonical source of functional time. The preserved functional timestamps generated by the lifecycle operations — `requested_at`, `decided_at` and the `recorded_at` of grant and revocation confirmations — take one `transaction_timestamp()` value per operation (the stable start instant of its transaction, not its commit time), assigned explicitly by the application, without database defaults or triggers; a grant confirmation reuses that instant as the start of the effective validity. Both sides are now materialized. `FunctionalTransactionTime`, in `App\AccessGovernance\Concurrency`, reads `transaction_timestamp()` from the transaction already owned by the calling Action and refuses to run outside one; `CreateAccessRequest`, `DecideAccessRequest`, `ConfirmExternalAccessGrant` and `RecordExternalAccessRevocation` read it once per operation. `CreateAccessRequest` also evaluates the active-access half of `RN03` against that same instant, and `ConfirmExternalAccessGrant` uses it for both `recorded_at` and the validity end. On the read side, ADR-008 already takes `projection_reference_at` from the same function, so ADR-008 and ADR-009 are materialized for reads and writes alike, including both read projections (`UC-005` and `UC-006`).

The application entry boundary baseline is recorded in [ADR-010](adr/0010-application-entry-boundary-baseline.md): the future REST/JSON interface is an entry adapter over the existing Actions and projections, not a second domain layer. It requires the authenticated context, validates only the shape of the transport input and translates results and known failures into HTTP, while the Actions keep the business rules, the lifecycles and their own transactions. The current actor is always the Actor Reference resolved from the authenticated external identity through `actor_references.external_identity_key`, which stays opaque; a client never supplies it, and an identity that cannot be resolved unambiguously fails closed, with no automatic provisioning. Authentication proves who the actor is, while authorization stays with the product's own sources — the resource's owner, `governance_memberships` and the request's requester — and with the scopes of the `UC-005` and `UC-006` projections. Business routes, including the access catalog, are protected by default under an `/api` surface that returns JSON, with no versioning chosen; `/up` stays outside that surface as operational infrastructure. Output is explicit and minimal and does not expose `external_identity_key`. ADR-010 itself is a decision only: when it was recorded there was no authentication, identity resolution or product API, and their later materialization, with the partial status of `RNF-001` and `RNF-002`, is described below.

The authentication baseline is recorded in [ADR-011](adr/0011-authentication-baseline.md): authentication is federated through OpenID Connect, with the Laravel backend as a confidential Relying Party using the Authorization Code Flow with PKCE, `state` and `nonce`; StewardArc stores no user credentials and no identity provider is chosen. In the MVP, the web client and the API are presented to the browser under one logical origin behind a common edge — a constraint on the browser surface, not a physical topology; the local Compose environment is unchanged. After login, the backend keeps the authenticated context in a server-side application session referenced by a protected cookie (`HttpOnly`, and `Secure` with TLS outside the local environment), regenerated on login and invalidated on logout; the web client receives no access token, stores no token and needs no CORS, and no refresh token is kept. The canonical external identity is the pair (`iss`, `sub`), which `external_identity_key` represents deterministically — its exact encoding is left to the implementation — and provider claims are never functional authority. State-changing authenticated operations require CSRF protection, and the baseline must be testable without an external identity provider, Internet access or personal secrets. ADR-011 itself adopts no package, including Sanctum, and implemented nothing when it was recorded; its later materialization, with the partial status of `RNF-001` and `RNF-002`, is described below.

The authenticated actor foundation of ADR-011 is materialized in `App\Authentication`: `ExternalIdentityKey` builds the persisted `oidc:v1:<base64url(iss)>:<base64url(sub)>` representation of an identity (see [data-model.md](data-model.md)), and `ActorReferenceResolver` resolves it through `external_identity_key` to exactly one existing Actor Reference, failing closed with `UnresolvedExternalIdentity` and never creating one. `ActorReference` is the principal of Laravel's session guard (`config/auth.php`: the `web` session guard over an Eloquent provider of Actor References), without password or remember token: password authentication always fails and the session keeps only the Actor Reference `id`. The local environment keeps sessions server-side in files with `SameSite=Lax`, while the automated suites keep the in-memory session.

The OpenID Connect login lifecycle of ADR-011 is materialized on `facile-it/php-openid-client` (`^1.0`), wrapped in `App\Authentication\OpenIdConnect`. `OpenIdConnectClient` discovers the provider — refusing a discovery document that names another issuer — builds the authorization request and, on callback, exchanges the code with `client_secret_basic` and the PKCE verifier; the library validates the ID Token (RS256 only, signature through the provider's JWKS, `iss`, `aud`, `exp`, `iat`, `nbf`, `nonce`) and StewardArc adds the checks the library leaves out: `nonce` must be present, and `azp` must name the client when present or when there are several audiences. `OpenIdConnectLogin` owns the login transaction — `state`, `nonce` and an S256 PKCE verifier, each 32 random bytes in unpadded Base64URL, kept in the session for at most ten minutes and consumed only by a callback that carries its exact `state`, whether that callback brings a code or a provider error, so a response without the right `state` cannot cancel the pending login — and resolves the validated (`iss`, `sub`) to a pre-provisioned Actor Reference, which is then logged in without remember-me. The `web` routes `GET /auth/login`, `GET /auth/callback` and `POST /auth/logout` (CSRF-protected, local logout only) redirect to `/` and fail closed with one generic response; only the `openid` scope is requested, UserInfo is not used, tokens, codes and claims are neither kept nor logged, and the authorization response is kept out of the session. The `OIDC_*` settings are read only when the login is used, so the rest of the application starts without them, and the tests use a fake provider with an ephemeral RSA key and no network. The login lifecycle itself adds no product API, local identity provider or user interface.

The first protected product API materializes ADR-010 and ADR-011 for `UC-005`. `bootstrap/app.php` loads `routes/api.php` under `/api`, with route names prefixed `api.`, on the `web` middleware group — encrypted cookies, the session and CSRF protection — plus `auth`. The result is a stateful session API on the session of the OpenID Connect login, protected by default for every route in that file, with no Sanctum and no bearer token; Laravel's own `api` group, which has no session, is deliberately not used. Guests are never redirected (`redirectGuestsTo(null)`), so an unauthenticated `/api` request gets `401` with `{"message":"Unauthenticated."}` whatever its `Accept` header, and `HandleCors` is removed from the global middleware, so no CORS policy is emitted — not even the framework's default one for `api/*` — on this same-origin surface. `GET /api/me/requests-and-accesses` is an invokable controller that takes the current actor from the session only (`#[CurrentUser]`) and calls `FollowMyRequestsAndAccesses`, whose read transaction and full materialization (ADR-008) are unchanged; only then is the result mapped, by an explicit allow-list, to a minimal JSON contract. The contract is `{"requests": [...]}`; each request has `id`, `access_profile` (`id`, `name`), `resource` (`name`), the Requester's `justification` as stated, `approval_flow`, `requested_duration_seconds`, `current_state`, `requested_at`, `granted_access` (`valid_until_at` and `state`, or `null`) and `history`. Each history entry has `kind`, `occurred_at`, `actor` (`id` and `display_name`, or `null` for the expiration milestone) and `decision` (`stage`, `outcome` and the decision's own `justification`, or `null` for any other kind). The projection reference instant, fact identifiers, the resource and Granted Access identifiers and `external_identity_key` are not exposed. Instants are RFC 3339 in UTC to the second, the precision they are stored with. Requests are ordered by `requested_at` and then `id`, and history entries by `occurred_at`, with no meaning in ties. The collection is not paginated, since the MVP has no performance requirement and the projection is a single snapshot, and a Requester without requests gets an empty collection. The tests cover guests with any `Accept` header, missing, unknown, expired and logged-out sessions, an end-to-end OpenID Connect login, client-supplied actors, the scopes of two requesters, the exact contract and the structural guarantees of the `/api` surface. `RNF-001` is therefore materialized for this endpoint only, as the other operations still have no HTTP surface. `RNF-002` stays partial: the session is server-side, its cookie is `HttpOnly` with `SameSite=Lax`, identity provider tokens are discarded and the surface is same-origin with structural CSRF protection, but TLS, `Secure` cookies in production and the production session store depend on deployment.

The optional local OpenID Connect demonstration materializes, for development and demonstration only, the demonstration identity provider that ADR-011 left open; the production identity provider stays open. It is Keycloak 26.7.4 (`quay.io/keycloak/keycloak:26.7.4`) in development mode under the `idp` Compose profile only: nothing depends on it, the normal stack and CI never start it, and its `dev-file` database lives inside the container, so recreating the container imports the realm again. Browser and backend share one issuer, `http://idp.stewardarc.test:8080/realms/stewardarc-demo`, fixed by `KC_HOSTNAME` and resolved through a hosts entry on the host, where the port is published on `127.0.0.1` only, and through a Docker network alias in the containers; no issuer is rewritten and the OpenID Connect code is unchanged. The imported `stewardarc-demo` realm (`keycloak/stewardarc-demo-realm.json`) has one confidential client, `stewardarc-backend`, limited to the Authorization Code flow with S256 PKCE, one exact redirect URI and no web origins, refresh tokens, implicit, direct access or service account flows. Its client secret and the user passwords are deliberately public, demo-only values, and no admin account, role, group or custom mapper is created. The two users have fixed IDs, so their `sub` is known and survives re-imports. `demo-requester` gets its Actor Reference from `Database\Seeders\LocalOidcDemoSeeder`, which runs only explicitly, in the `local` environment and with the demo issuer configured. `demo-unprovisioned` is authenticated by the provider but rejected by StewardArc, since no Actor Reference is ever created on login and nothing the provider asserts is functional authority. The automated suites keep the fake provider, so CI stays offline.

The operational observability baseline is recorded in [ADR-012](adr/0012-operational-observability-baseline.md): operational telemetry stays separate from the Functional History, so no correlation identifier, operation name or log record ever becomes a functional fact, and telemetry gets no domain table and no migration. One execution is one execution of an entry point — an HTTP request, or a critical Action invoked with no execution already around it — and it carries one `execution_id`: an opaque, server-generated UUIDv4, never persisted, never reused, not tied to the session or to the Actor Reference, not returned to the client and never taken from a client header, since a caller must not decide how operational evidence is grouped. It also carries an `operation`, which reuses the existing route names on HTTP and stable names for the four critical Actions, with no second vocabulary and no central registry. Operations nest, the innermost one names what is effectively running, and an unexpected failure of a critical Action is reported while that Action's own context is still active, once per exception. Expected failures — an unauthenticated request, a missing CSRF token, an expected absence, a business rule violation, an identity with no Actor Reference, an invalid OpenID Connect callback — are not operational errors; an unexpected failure produces one `ERROR` record, and a closed allow-list of OpenID Connect reasons produces a `WARNING` carrying a fixed reason code and nothing else. Records start from an allow-list — `execution_id`, `operation`, a fixed reason code, the SQLSTATE, the exception class and the code reference needed for diagnosis — and never carry credentials, tokens, session artifacts, the callback query, `external_identity_key`, the pair (`iss`, `sub`), display names or justifications; the internal Actor Reference identifier is admitted narrowly, as a pseudonymous diagnostic value, and is never the correlation identifier. The raw report of a database failure is explicitly rejected, because it can carry the statement with its binding values and the driver's own message; its record is sanitized instead. The operational instant is the record's own, the current text log format is kept, `/up` stays outside the correlated surface, and the materialization must be automatically verifiable. ADR-012 itself is a decision only; its materialization, with the resulting status of `RNF-006`, `RNF-010` and `RNF-011`, is described below.

The operational observability baseline of ADR-012 is materialized in the application. `App\Observability\OperationContext` runs a callable as one operation over the framework's own log context, inside a context scope: it reuses the current `execution_id` or generates a UUIDv4 when there is none, sets the `operation`, reports an unexpected failure before the scope gives the previous context back, and rethrows the very same exception; it touches no database and persists nothing. `App\Http\Middleware\TrackExecution` is prepended to the `web` group, so every login and product request — its session, authentication and CSRF protection included — is a new execution whose operation is its route name; `/up`, which has no middleware group, stays outside, no correlation header is ever read and nothing about the execution is returned to the client. The four critical Actions wrap their unchanged transactions in their own operations (`access_request.create`, `access_request.decide`, `access_grant.confirm`, `access_revocation.record`), so a failure is recorded under the Action's operation, within the execution of the request when there is one and as an execution of its own when the Action is called directly. `bootstrap/app.php` keeps the policies together: the four business-rule refusals are not reported (the framework already ignores the authentication, CSRF, validation and not-found failures), one `Throwable` instance produces at most one record (`dontReportDuplicates()`), and a `QueryException` produces only the sanitized `Unexpected database failure.` record of `App\Observability\DatabaseFailure` — the exception class, the SQLSTATE read from the driver's error information and the first application frame as a relative path and line — while the raw report, with its statement, values, driver message and connection details, is suppressed. The `pgsql` connection masks binding values in exception messages, and exception traces carry no argument values (`zend.exception_ignore_args`), so no justification or identifier reaches a record through a trace. The OpenID Connect controller records, from the same catches and behind the same generic `401`, a fixed reason and nothing else: `configuration`, `provider_metadata` and `token_exchange` as one `ERROR`; `state_mismatch`, `id_token`, `identity_claims` and `unresolved_external_identity` as one `WARNING`; and nothing for the other reasons or for a successful login or logout. The log format and channels are unchanged. The tests capture the records through the application's own logger and processors with Monolog's `TestHandler`, and prove the correlation, the nesting, the reporting of a directly invoked Action, the suppression of duplicates, the absence of errors for expected failures, the sanitized database record and the absence of sentinel secrets, tokens, identities and justifications; the PostgreSQL suite writes no log file. `RNF-010` and `RNF-011` are therefore materialized for the current application, a single-process monolith with no distributed tracing. `RNF-006` is materialized only in part: the application keeps to its allow-list, but the production log destination, access, retention, rotation, shipping, `APP_DEBUG=false` and the rest of the secure production configuration depend on the deployment.

A minimal continuous integration baseline automates the executable validations that already exist, following the testing baseline of ADR-006. The GitHub Actions workflow [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) runs on pushes and pull requests to `main` and on demand, with read-only repository permissions and no secrets. It reuses the local Docker Compose environment: it builds the backend, installs the locked dependencies, starts PostgreSQL and the backend, creates and migrates the dedicated `stewardarc_test` database, checks that `/up` returns 200, runs the scaffold's stock tests and the full PostgreSQL suite — including its concurrency tests — and lints and builds the frontend. It does not deploy, publish or release anything.

## Known conceptual boundaries

- **Access Governance** is a cohesive core: access requests, decisions, grant confirmation, Granted Access, effective validity, revocation confirmation, expiration and functional history.
- **Catalog** (resources and access profiles) is only a **candidate reference boundary**. It is not a separate service.
- **Authenticated identity** is external to the domain; **authorization** belongs to the product.
- **Target systems**, where grants and revocations actually happen, are outside StewardArc.
- **Operational telemetry** is a concern separate from the functional history.

The minimum implementation baseline defines three code locations — `App\Models`, `App\AccessGovernance\Actions` and `App\AccessGovernance\Concurrency` (see [ADR-006](adr/0006-application-implementation-baseline.md)). The authentication foundation adds a fourth, `App\Authentication`, for the entry-boundary identity mechanisms of ADR-010 and ADR-011; it holds no business rule. The HTTP entry adapter lives in `App\Http\Controllers`, with the product API under `App\Http\Controllers\Api`, and holds no business rule either. The operational observability of ADR-012 adds `App\Observability`, with the operation context and the sanitized database failure record, and `App\Http\Middleware`, with the middleware that starts each HTTP execution; neither holds a business rule. Further module organization, packages, namespaces and layers remain open until a real need appears.

## Deliberately open decisions

The following are intentionally not decided:

- version update and maintenance policy for the stack;
- physical deployment, including how the frontend and backend are hosted behind the common edge required by ADR-011, the reverse proxy, TLS termination, and cloud or hosting;
- the remaining authentication decisions: the production identity provider, the production session store, lifetime and timeouts, production cookie hardening such as a `__Host-` prefix, and the production provisioning mechanism for Actor References (the entry boundary is decided in ADR-010 and the authentication baseline in ADR-011; the OpenID Connect login, the first protected product API and the local demonstration identity provider with its demonstration identities are materialized as described above);
- federated logout (RP-initiated, back-channel or front-channel), MFA and step-up authentication, SCIM or other identity synchronization, and rate limiting;
- the operational mechanism for provisioning and removing Governance memberships, and any temporal history of them (the authority source itself is decided in ADR-007);
- whether a resource can have more than one Resource Owner beyond the MVP, which models exactly one (see ADR-004);
- any future proactive or operational time-based processing (`A2` is already derived from the effective validity period and time; see ADR-003);
- retry policy, including deadlock retry, and transport idempotency keys (the concurrency baseline itself is decided in ADR-005);
- custom lock timeout and wait tuning (the baseline uses blocking advisory acquisition; see ADR-006);
- detailed API contracts for the operations that still have no HTTP surface, including endpoint paths, payloads, HTTP status mapping, the error envelope beyond the `401` of the `/api` surface, versioning, pagination and presentation order (the protected `/api` JSON surface is decided in ADR-010, and the login routes and the `UC-005` endpoint are materialized as described above);
- the HTTP representation of the `UC-006` projection (the `UC-005` representation is materialized above, and the isolation of both projections is decided in ADR-008);
- caching and materialized views;
- future schema evolution beyond the approved persistence baselines, including performance indexes beyond those motivated by integrity;
- the operational observability decisions that depend on deployment or on a platform: the production log destination, whether it is a file or standard output, a production log format such as JSON, rotation, retention and log shipping, any external observability platform, alerting, dashboards, metrics, distributed tracing and OpenTelemetry, an edge or proxy correlation identifier, observability of the frontend and user activity analytics (the baseline itself — what an execution is, its identifier, the operation names, the failure classification and the telemetry allow-list — is decided in ADR-012 and materialized as described above);
- test coverage policy and thresholds, and test organization beyond the baseline (which already distinguishes pure unit tests from PostgreSQL integration and concurrency tests; see ADR-006);
- CI beyond the minimal baseline, such as branch protection, required checks, build matrices, caching, dependency auditing, repeated concurrency runs and any release or deployment pipeline.

Each should be decided when a real need arises and recorded as an ADR when it is architecturally significant.
